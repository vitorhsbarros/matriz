# Matriz 1.1.0 — Release notes

**Version:** `1.1.0`, Git tag `v1.1.0` on `main`, released on 2026-11-16.
**Release candidate:** `1.1.0-rc.1`, Git tag `v1.1.0-rc.1`, published on 2026-11-15 as a GitHub pre-release.
**Image:** `ghcr.io/vitorhsbarros/matriz:1.1.0` (also `latest`), for `linux/amd64`.

## Version number

Matriz follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The previous release is `1.0.1`.

| Kind of change | In this release | Version part |
|---|---|---|
| Breaking: the API, the data or how the application is configured stop working as before | None. The API (`openapi.yaml`) is unchanged, no database migration was added, and every setting from `1.0.1` works as before | Major stays 1 |
| New, backward-compatible capabilities | The container image, Docker Compose for the whole application, the CI image and publication jobs, two public health checks, and JSON logs in the container | **Minor: 0 → 1** |
| Fixes only | — | Patch back to 0 |

So the version is **1.1.0**. The release candidate carried the `-rc.1` suffix, a pre-release that sorts before `1.1.0`.

## What's new

- **Container image.** A multi-stage `Dockerfile` builds the JAR, with the browser application inside, and runs it on a Java 21 runtime as a non-root user. The image has no source code, build tools or `.env`, and installs the Ubuntu security updates.
- **Docker Compose.** `docker compose --profile app up -d --wait` starts the application and PostgreSQL, and returns once both are healthy. Both are reachable from the same machine only (`127.0.0.1`). `docker compose up -d --wait`, without the profile, still starts only PostgreSQL.
- **Continuous integration.** On every push and pull request to `main`:
  - the tests, Semgrep, CodeQL and OSV-Scanner run first;
  - then the image is built, scanned for known vulnerabilities, and tested with Docker Compose.
- **Publication.** Publishing a GitHub release pushes that tested image to the GitHub Container Registry, tagged with the version and the commit, and `latest` for a final release.
- **Health checks.** `/actuator/health/liveness` (the application is running) and `/actuator/health/readiness` (it can serve requests, which needs the database) can be read without logging in, and show only their status.
- **Logs.** In the container, the logs are JSON lines in the Elastic Common Schema. Outside it, they stay plain text.

The application's features are the same as in `1.0.1`. Every change is listed in [CHANGELOG.md](../../CHANGELOG.md).

## How to run it

With Docker only, from a copy of the repository and a `.env` made from `.env.example`:

```bash
docker pull ghcr.io/vitorhsbarros/matriz:1.1.0
docker tag ghcr.io/vitorhsbarros/matriz:1.1.0 matriz:local
docker compose --profile app up -d --wait --no-build
```

Then open `http://localhost:8080/`. Building the image locally, the health checks, the logs and the smoke test are described in [README.md, "Running with Docker"](../../README.md#running-with-docker).

## Known issues and open points

- **Not deployed.** The deployment platform is still to be decided (PD13). TLS, the production database, its backups and the secret store depend on that decision.
- **Readiness while the database is down.** It answers `DOWN` after 30 s, the connection pool's time-out. The image's health check still marks the container unhealthy. A platform probing with a shorter time-out would see a time-out instead.
- **amd64 only.** On an arm64 machine the image runs under emulation, which is slower.
- **Supply chain.** The image has no signature or provenance attestation. The image scan doesn't see the Java runtime, and the Java libraries are scanned by the dependency job instead.
- **Version shown by the application.** `pom.xml` still says `0.1.0-SNAPSHOT`, which the JAR's name and the logs' `service.version` show.

The full list, with the evidence, is in [docs/delivery-plan.md, "Delivery"](../delivery-plan.md#10-delivery).
