Enquadramento

Como o Jira, mas muito mais simples.

Para equipas pequenas: sem sprints nem configuração, só o essencial.

Projetosmembros e gestor
Tarefasquadro de três estados
Responsáveispessoas e equipas
Comentáriosdiscussão por tarefa

O problema: equipas pequenas para quem o Jira traz sprints, relatórios e configuração de que não precisam. O Matriz guarda só o necessário: projetos com membros, tarefas num quadro com prioridade, responsáveis (pessoas ou equipas) e comentários. Sem sprints, relatórios nem fluxos configuráveis.

O MVP tem 23 histórias de utilizador, todas utilizáveis no browser. Agora mostro-o a funcionar.

Fontes: README.md (introdução, "Problem", "Goals", "MVP features"), docs/user-stories.md.

Demonstração · em produção

Matriz a funcionar.

matriz-2s4n.onrender.com
  • Ana: criar, mover e atribuir uma tarefa.
  • Rui e Sara: regras de acesso.

2 minutos. Mudar para o separador da aplicação, já aberto e com sessão iniciada como Ana.

Fluxo 1 (Ana, gestora de Website): dashboard com contagens → Website → New task (prioridade High) → arrastar para In progress → abrir a tarefa → atribuir ao Rui e à equipa Design (criada na véspera; os dados demo não têm equipas) → comentar.

Fluxo 2: Rui (membro) abre Website: vê e muda tarefas, mas não tem Edit nem Delete. Sara (não membro): o dashboard está vazio e o endereço de Website dá "Project not found.".

Guião completo: docs/presentation/demo-script.md. Fontes: README.md ("Demo accounts"), docs/user-stories.md.

Um monólito modular: uma aplicação, uma base de dados, quatro módulos de negócio, com fronteiras verificadas pelo ModularityTest (Spring Modulith) em cada build (ADR-0001). O React vai dentro do mesmo JAR, servido pelo Spring Boot. Sessões no servidor com cookie Secure/HttpOnly e token CSRF (ADR-0002). Esquema da base de dados por migrações Flyway, uma pasta por módulo.

Entrega: imagem Docker multi-stage, sem root; o GitHub Actions corre testes, SAST, SCA, scan e teste da imagem, e numa release publica-a no ghcr.io com atestação; o Render corre essa imagem com PostgreSQL (PD13).

Versões: React 19.3, TypeScript 5.9, Vite 8.3, Spring Boot 4.1.2, Java 21, Spring Security 7.1, Spring Modulith 2.1.2, PostgreSQL 17.10, Flyway 12.4. Fontes: README.md ("Technologies"), docs/architecture.md §1 e §5, docs/constraints.md (PD13).

Desafio 1 · Erros da IA

A IA também erra.

Hikarium time-out inválido de 5s
Shelldois argumentos lidos como um só
Testeum caso fora da especificação

Solução: exigir evidência antes de aceitar.

Três erros reais, registados: o time-out escrito "5s", que o Hikari não aceita (só milissegundos), impediu o arranque e foi corrigido para 5000 (verification.md §20); uma verificação inválida porque a shell passou dois argumentos como um só (verification.md §12); um teste com um caso (um título só com um tab) que a especificação não suporta, removido (verification.md §10).

Todos foram apanhados pela evidência: o arranque falhado, a verificação repetida, a comparação com a especificação.

Desafio 2 · Carga cognitiva

A decisão é minha.

44decisões registadas
13decisões que a IA não podia tomar
  • Opções com recomendação
  • Plano antes de mudar
  • Aprovar antes de publicar

Solução: delegar o rotineiro, decidir o essencial.

A carga cognitiva: a IA propõe muito, e cada aprovação pede atenção. Ficaram registadas 44 decisões e aprovações minhas em 12 documentos. E 13 decisões técnicas (PD01–PD13) que só eu podia tomar: 9 tomadas, como a stack (Java 21, Spring Boot, PostgreSQL, React), a sessão que termina após 30 minutos sem pedidos, as palavras-passe com BCrypt e a plataforma de deploy (Render); 4 em aberto, todas fora do MVP, como apagar contas ou limitar tentativas de log-in.

Para não bloquear nem perder o controlo: o agente apresenta opções com uma recomendação (AGENTS.md §3), um plano antes de mudanças grandes (§4) e pede aprovação antes de push, releases ou publicação (§6). Eu decido o essencial; o rotineiro segue a recomendação.

Fontes: docs/constraints.md §4, AGENTS.md §3, §4 e §6; contagem das frases de aprovação em docs/.
